# 阶段0 - 项目体检清单

先跑 `scripts/preflight_check.py <项目根>` 自动扫描, 再人工确认下面几项。
目标: 判断"距离内网 SSO 部署给多用户用"还差哪些, 不要凭感觉直接动手。

## 必查七项

1. 技术栈与启动方式 — 框架(Streamlit/FastAPI/Flask/Django)、入口、监听端口、包管理(uv/pip)。
   Streamlit 是特例: 它自己掌控请求生命周期, 拿不到 request, 无法插鉴权中间件 -> SSO 必须放 nginx 层。
2. 鉴权现状 — 有没有任何 login/session/token。多数本地工具是"零鉴权", 任何人可访问。
3. 用户与数据隔离 — 有没有 user 概念? DB 表有没有 owner 字段? 文件是否按用户分目录?
   多用户共享部署最大的风险就是"A 能看到 B 的数据"。
4. 存储后端 — SQLite 只适合单机; 多用户并发写会锁竞争 -> 换 MySQL。文件落本地还是对象存储。
5. 打包制品 — 有没有 Dockerfile / compose。没有就要新建(用 assets/ 模板)。
6. 外网出口 / 重依赖 — 有没有调外网 API(内网要走代理或关)? 有没有 GPU 版 torch / nvidia-*-cu12
   这类几 GB 的依赖(无 GPU 部署要瘦身, 见 04)。模型权重要不要预下载烤进镜像。
7. 配置化程度 — DB/SSO 等关键项是不是硬编码? 必须能从环境变量读, 区分本地/线上。

## 体检产出

把缺口列成清单, 对应到后续 references:
- 缺隔离 -> 02
- 缺 SSO -> 03
- 构建/依赖问题 -> 04
- 工单/上线 -> 05

## 关键判断: 改造 vs 重写

- 只是"上线 + 加鉴权 + 隔离" -> 在原项目上改造(推荐, 风险小)
- 用户坚持换前端框架(如 Streamlit->React) -> 那是重写, 工作量 x5, 先确认是不是真需要。
  通常先用现有框架 + SSO + 隔离上线(P0), 跑一个月看真实反馈再决定要不要重写(P1)。
