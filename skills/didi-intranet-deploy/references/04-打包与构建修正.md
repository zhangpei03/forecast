# 容器化打包与构建常见修正

用 assets/Dockerfile.template + deploy/ 模板做单容器(nginx+sidecar+后端)。
下面是内网构建最容易卡的几个点和修法。

## 1. 公网基础镜像拉不动 (最常见)
内网构建机访问 docker hub 超时。解法:
- Dockerfile 用 `ARG BASE_IMAGE`, 生产传 `--build-arg BASE_IMAGE=hub.xiaojukeji.com/base/python:3.12-slim`
- 本地若已有某 tag(如 python:3.12-slim-bookworm), 默认用它避免重新拉
- 同理 MySQL 等镜像也用本地已有或内网 tag

## 2. GPU 版 torch + nvidia-*-cu12 拖垮构建 (ML 项目必踩)
autogluon/torch 在 linux 默认拉 GPU 版 torch + 几十个 nvidia-*-cu12 包(数 GB),
无 GPU 的 OE 部署纯属负担, 且常卡死构建。解法: 钉 CPU 版 torch。
在 pyproject.toml 加:
```
[tool.uv.sources]
torch = [{ index = "pytorch-cpu" }]

[[tool.uv.index]]
name = "pytorch-cpu"
url = "https://download.pytorch.org/whl/cpu"
explicit = true
```
关键: 若 torch 是传递依赖(autogluon 带的), sources 可能不生效 ->
把 `torch` 显式加进主 dependencies, 再 `rm uv.lock && uv lock` 重新解析。
验证: `grep -c 'name = "nvidia-' uv.lock` 应大幅下降, torch 变成 `2.x+cpu`。
效果: 镜像从 ~6GB 降到 ~2GB, 构建从"卡死"到几分钟。

## 3. uv 走内网 PyPI
`ENV UV_INDEX_URL=https://pypi.intra.xiaojukeji.com/simple`(按实际内网源)。
requirements.txt 要 pinned(==)。

## 4. 架构: 本地 arm64 vs OE amd64
Apple Silicon 本地 build 默认 arm64, 不能推给 amd64 的 OE。
必须 `docker build --platform linux/amd64 ...`。compose build 出的本机架构镜像不能直接推生产。

## 5. 模型权重预下载
若用 AutoGluon/HF 等首跑联网拉权重, 内网拉不到会运行期挂。
构建期跑 `scripts/prefetch_models.py`(失败不阻断), 把权重烤进镜像。

## 6. 镜像推送
登录 hub.xiaojukeji.com 后:
```
docker build --platform linux/amd64 -t hub.xiaojukeji.com/<user>/<app>:v1 .
docker push hub.xiaojukeji.com/<user>/<app>:v1
docker manifest inspect hub.xiaojukeji.com/<user>/<app>:v1   # 验证远端存在 + 架构
```

## 7. 后台长构建怎么跑
build 很久时不要盲等。用 `docker compose build 2>&1 | tee /tmp/build.log | grep ...` 在前台跑并
过滤关键行; 同时另开终端用 `docker buildx du` 看 cache 是否增长判断是否真在干活(停滞=网络卡)。
避免同时跑两个 build 抢 buildkit 锁导致互相停滞。

## 本地整链路验证 (强烈推荐上线前做)
用 docker-compose 起 后端容器 + MySQL + 一个 mock-sso(按 cookie/参数返回不同用户名),
就能不接真 SSO 验证: 未登录拦截、登录回跳、X-SSO-User 透传、多用户数据隔离。
mock-sso 让 ticket 编码用户名(如 tkt-<user>), 不同用户拿不同 ticket, 才能验隔离。
